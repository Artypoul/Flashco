# Flashco v0.9.3 — состояние реализации

Состояние интеграции на 19 ноября 2026 года. Текущий source SHA, ревью и состояние проверок следует брать из [PR #16](https://github.com/Artypoul/Flashco/pull/16) и связанных с его head [запусков Actions](https://github.com/Artypoul/Flashco/actions). Локальные результаты ниже не заменяют проверки точного опубликованного SHA; готовность A определяется этими доказательствами, а клиентская готовность B требует отдельных проверок устройства и подписанного выпуска.

Основание — [утверждённый план](https://github.com/Artypoul/Flashco/blob/511e7601b6ed72ee410499d825a9db145a9e1df9/docs/upstream/2026-11-18-v0.9.3-update-plan.md), база Flashco `871a89e4d7da3fe4a484c193b2fbeccc57129c5b`, начальный head PR `1d6e6a9a6c59d213930759830fa0748e977abc73`. Выбрана версия исходников `0.9.3+2026111901`; это не опубликованный релиз и не подтверждение наличия пакета.

## Состав текущей интеграции

- Перенос стабильного FlClash v0.9.3 `be84736605527034689c95bf27828ff27d912c5e` с сохранением собственных политик в `lib/flashco` и `modules/flashco_core`. Gitlinks: Core `024245dc72bc92f48237f865119afe0cd53ac9e6`, Prism `63450c0ac0e8e1b2c0f3ed4ad7926dc94e083185`; локальных патчей исходников подмодулей не предполагается.
- Схема SQLite — 23; версия миграции настроек — 2. Они независимы. Переходы со схем 20/21/22 сохраняют собственные правила и поддерживают известные варианты старых MITM-таблиц. Проверки охватывают повторное открытие, сбой и откат миграции, совместимость настроек и старых ZIP.
- Сохраняются согласие, свежая установка, вручную введённая или встроенная подписка, fallback, явные пользовательские значения и REALITY defaults; профиль проходит преобразования до передачи в Core. Сохранённые настройки Access отображаются при повторном открытии; выбранные пустые TUN-значения сериализуются явно. Маркер `personalDefaults.initializing` позволяет возобновить незавершённую инициализацию свежей установки. Владение жизненным циклом Android остаётся у `ServiceState`, восстановление и конкурирующие команды проверяются в этом контракте.
- Updater выбирает существующий универсальный Android APK и совместимый Windows installer, требует строгий TLS и соответствующий SHA-256 из `SHA256SUMS`; для несовместимых personal/first-run/REALITY/test вариантов не предлагается автоматическая generic stable-установка. SHA-256 не подтверждает подпись APK.
- Существующие personal workflow остаются ручными. CI использует рекурсивный checkout Prism и CA bundle, проверенный закреплённым SHA-256. В существующем `build.yaml` подготовлены три candidate-варианта из одного проверяемого source SHA: Android first-run/REALITY, Android со встроенной синтетической тестовой подпиской и Windows EXE/ZIP с той же синтетической тестовой подпиской. Они не используют личные секреты и записывают вариант, defines, исходный SHA и хеши; конкретные артефакты и их содержимое проверяются по run и source SHA в Actions.
- `release.yaml` остаётся отдельным ручным выпуском из `main`: подписанный universal APK и Windows EXE/ZIP проходят существующие проверки, результатом является draft. Разрешение на merge или публикацию не подразумевается.

## Полный снимок и возврат тестовой установки

Штатный ZIP export сохраняет снимок базы, конфигурацию/версию и связанные файлы профилей и скриптов, но **не все platform preferences**. Успешный импорт ZIP не доказывает полный откат.

Перед первым тестовым обновлением на согласованном изолированном стенде:

1. Остановить тестовые приложение, Core и Helper и закрыть соединения SQLite. Сохранить согласованную SQLite-копию вместе с относящимися WAL/SHM при необходимости либо использовать корректный SQLite snapshot; не копировать одну живую БД.
2. Сохранить `profiles/<id>.yaml`, `scripts/<id>.js`, локальные providers и другие файлы, на которые указывает конфигурация; отметить, какие provider caches восстанавливаются, а какие можно воспроизвести.
3. Экспортировать **всё** хранилище preferences конкретной платформы, включая `bundledSubscription.<hash>`, `bundledFallback.<hash>`, `personalDefaults.v1`, `personalDefaults.initializing` и `subscriptionOnboarding`. На Windows/Linux это `shared_preferences.json`; Android/macOS используют нативное хранилище plugin, поэтому один JSON не покрывает все платформы. Не включать личные данные в Git или публичные Actions artifacts.
4. Составить приватный manifest снимка с версией/build, платформой, фактической identity установки, составом файлов, SHA-256 и способом получения согласованного состояния.
5. В изолированной установке после обновления восстановить снимок и открыть его старым совместимым бинарником: проверить профили, скрипты, правила, выборы и настройки, отсутствие повторного onboarding/import; затем повторить обновление. Возврат одного APK/EXE не откатывает схему 23. Не удалять таблицы и не менять `user_version` автоматически.

Эта процедура описана для проверки; её выполнение и полноценное восстановление на тестовом стенде пока не подтверждены.

## Критерии готовности A и B

Для A требуется доказательство для одного точного source SHA: успешные проверки генерации/чистоты inputs, analyzer, полного Flutter suite и coverage, обоих REALITY defines и реальных Go fixtures, native checks и независимого итогового ревью. В [PR #16](https://github.com/Artypoul/Flashco/pull/16) и его [Actions](https://github.com/Artypoul/Flashco/actions) сопоставляют head SHA, состояние каждого задания и артефакты трёх candidate-вариантов: run ID, имена, checksum, defines, Android package ID, signer, версии и ABI, Windows metadata. Отсутствие конкретного результата не считается успехом; личные данные и ключи в эти пакеты не добавляются.

Для B после отдельно разрешённых merge и release tag необходимы draft из точного SHA и проверка его подписанного APK, Windows EXE/ZIP, manifest и `SHA256SUMS`; сопоставление с реально выданным прежним пакетом по identity/signer/версии/ABI; update-in-place A→B, полный snapshot/restore старым бинарником; согласие, VPN permission, соединение, reconnect, start/stop и provider refresh на тестовых Android/Windows. Эти сценарии и публичная публикация не выполнялись. При отсутствии исходного официального APK, устройства или ключа ограничение остаётся открытым, а не заменяется чистой установкой.

## Windows numeric version: исходный контракт

Windows `VERSIONINFO` хранит каждую числовую часть в 16 битах. Исходный `0.9.3+2026111901` сохраняет полный build number для Android `versionCode`, строк версии и release manifest; числовые Windows `FILEVERSION`/`PRODUCTVERSION` задаются как `0.9.3.0`, с отказом компиляции при компонентах семантической версии вне `0..65535`. Повторные сборки одного `X.Y.Z` имеют одинаковую числовую Windows revision; для различения нужен полный строковый build. Установщик сохраняет существующее сравнение полных версий; закреплённый `flutter_distributor` передаёт значение версии pubspec в `APP_VERSION`. Candidate и release workflow должны проверять числовую и полную строковую версии **приложения из ZIP**, отдельно от версии самого Inno setup EXE. Реальная компиляция и метаданные Windows пакета проверяются по артефактам точного SHA в Actions.
