Дата проверки источников: 18 ноября 2026 года. Статус: **план для реализации**.

## 3. Обязательные функции Flashco

Канон требований — [PRODUCT.md](../../PRODUCT.md). Ниже перечислены критерии, которые должны пережить обновление.

| Функция | Сохраняемое поведение |
| --- | --- |
| Два варианта подписки | Прежние Android/Windows-сборки со встроенным URL и дополнительный Android first-run без URL. Режимы встроенного URL и запроса при первом запуске взаимоисключающие |
| Первый запуск | Запрос после соглашения только на новой opt-in Android-установке; отмена и ошибка допускают повтор; завершение после сохранения профиля. Обновление, удаление профиля и ручной выбор не запускают импорт повторно |
| Персональные настройки | Применяются один раз по состоянию хранилища до миграции. Сохраняются выбранные тема, язык, автозапуск, TUN, auto-route, strict-route, системный прокси и запрет обхода VPN |
| Fallback | Штатная упорядоченная группа по всем узлам и providers, возврат к приоритетному живому узлу, интервал 10 с, timeout 3000 мс, `lazy=false`, HTTP 204. Пустой список даёт `REJECT`; `DIRECT` и `Fastest` не становятся резервами |
| Число серверов | Искусственного ограничения нет. В основной ветке уже обходятся все серверы; тест на 350 узлах — пример регрессии, а не новый максимум |
| REALITY | Только при opt-in define добавляются отсутствующие ML-KEM/fingerprint defaults. Явные значения, включая `false`, сохраняются; HTTP/file/inline providers и их обновления покрыты; исходная подписка не переписывается |
| DIRECT | Российские домены/IP и адресные исключения остаются в редактируемых правилах. Сохраняются изменения, отключения, порядок и однократность backfill |
| Данные | Профили, URL, overrides, выбранные группы, пользовательские правила, markers и настройки не сбрасываются. Режим профиля с fallback остаётся стандартным |
| Идентичность | `com.follow.flashco`, каталоги данных, FlashcoCore/Helper, IPC, AppId, канал обновлений и signing остаются совместимыми с установленным Flashco |
| Windows | Сохраняются проверки версии/области/каталога, защита данных и работа только с Helper своей установки; подтверждённый downgrade не считается доказательством совместимости базы |
| Приватность | Firebase Analytics/Crashlytics не возвращаются. Внешняя проверка качества IP и Google ML Kit QR сохраняются по принятому решению; соглашение остаётся с одной кнопкой «Согласен» |
| Ранее удалённые функции | Не возвращаются продуктовая вкладка Safe, собственный failover, переключатель Fastest и редактируемые глобальные ML-KEM overrides. Защитный `SAFE_MODE` для разработки сохраняется |

Отдельная REALITY-конфигурация внутри XHTTP `download-settings` и явно выбранные старые fingerprints остаются за пределами существующего режима defaults. Обновление не должно обещать для них новую поддержку без реализации и проверки.

## 4. Границы собственного модуля

Выделение собственных функций согласовано в предшествующей задаче; оно нужно из-за пересечения Flashco defaults, подписки и маршрутизации с изменёнными donor bootstrap/setup/migration путями.

| Слой | Ответственность | Точки подключения |
| --- | --- | --- |
| `lib/flashco/` | Build flags, personal defaults, начальные DIRECT-правила, onboarding policy, выбор при импорте, fallback и REALITY transformations | `bootstrap.dart`, preferences, `providers/actions/profiles.dart`, `providers/actions/setup.dart`, финальное формирование YAML |
| `modules/flashco_core/` | Только собственная Go-политика определения ссылок на группы | Тонкий адаптер в `core/`, согласованный Dart/Go метод и контрактные тесты |
| Существующее хранилище | Запись профилей, preferences, транзакции и версии миграций | Остаётся у текущих owners; модуль не заводит вторую базу или независимый жизненный цикл |
| Платформенный runtime | Desktop Core lifecycle и Android `ServiceState` | Сохраняют владение start/stop/restart; модуль вызывает существующие интерфейсы |
| Mihomo submodule | Донорское ядро на точном SHA | Собственные политики Flashco хранятся вне `core/Clash.Meta` |

Для `lib/flashco` добавить измеренный coverage floor в `tool/check_coverage.dart`, сохранив существующие пороги. Для Go-модуля проверить build fingerprint/cache invalidation, `replace`/module path, форматирование, vet и тесты через реальный Core adapter. Новый каталог не должен выпадать из CI.

## 5. Критические места совместимости

### 5.1. Коллизия миграции SQLite 21

В [Flashco](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/database/database.dart) миграция 21 добавляет российские правила. В [доноре](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/lib/database/database.dart) миграция 21 создаёт `ipQualities`, 22–23 создают/меняют `mitmModules`. Копирование donor `from < 21` пропустит нужную таблицу на установленном Flashco 21.

Рабочая схема — оставить Flashco backfill 21 и перейти к 23 через собственные этапы: 22 создаёт отсутствующую `ip_qualities`, 23 создаёт или приводит к текущей форме `mitm_modules`. Перед фиксацией SQL проверить фактические таблицы и колонки, включая старые и частично существующие формы. Создание таблицы и обновление уже существующей таблицы — разные сценарии. Транзакция не должна оставлять частично обновлённую базу.

Обязательные fixtures: чистая установка, Flashco 20 и 21 с реальными данными, существующая старая форма новых таблиц, повторное открытие, прерывание/ошибка миграции. Сверять профили, overrides, выборы, rules/disabled rules и порядок до и после. Не переиспользовать номер схемы с иной структурой молча.

### 5.2. Версия preferences и новые overrides

Flashco использует `currentVersion=2`; донор — `1` и отдельный счётчик UI upgrades. Копирование donor migration может отклонить сохранённые данные Flashco как слишком новые. Сохранить совместимость версии 2, отдельно перенести нужные upgrade transforms и отказ от записи неизвестной будущей версии. Источники: [Flashco migration](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/common/migration.dart), [donor migration](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/lib/common/migration.dart).

Проверить TUN `false` и пустые списки, DNS hijack, сохранённый test URL, размеры/положение окна, тему, WebDAV credentials и first-run/personal markers. Отсутствующее значение и явно пустое значение не эквивалентны.

### 5.3. `profile.base` и итоговый YAML

[Новый Go-путь](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/core/profile_base.go) держит большие списки в Core и при объединении берёт `proxies`, `proxy-groups`, `sub-rules` из исходного профиля. Поэтому Dart-only преобразования Flashco могут исчезнуть.

Первый совместимый вариант: для профилей, которым нужны fallback или REALITY defaults, использовать полный путь конфигурации; обычные совместимые профили оставлять на `profile.base`. Это сохраняет поведение, но для персональных профилей откладывает часть экономии памяти нового пути. Переход всех профилей на оптимизированный путь допустим только после эквивалентных проверок финального результата.

Проверять итоговый YAML и поведение закреплённого Core, включая refresh providers, scripts/custom providers, root REALITY, явные overrides, сохранение DIRECT и ручного выбора. Обработать 0, 1 и много узлов, включая 350, без фиксированного ограничения. Полный путь тоже проходит проверку большой подписки; отказ от части оптимизации не разрешает вводить лимит или игнорировать сбой на больших данных.

### 5.4. Updater и пакеты Flashco

[Donor updater](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/lib/common/app_update.dart) строит имена assets по платформе/ABI. Personal Android Flashco выпускает universal APK. Согласовать поиск universal и ABI assets с реально публикуемыми пакетами Flashco; проверить checksum, подпись, AppId, версии и корректную ошибку при отсутствии совместимого пакета. Переход на FlClash release/installation identity недопустим.

Actions artifact и GitHub Release asset — разные источники. Общий CI сам по себе не создаёт Flashco release-пакеты: действующий release job ограничен donor repository. Публикация собственного release и изменение канала доставки требуют отдельного решения; план не включает загрузку персонального APK со встроенным URL в публичный release.

| 7. Проверить реализацию | Выполнить целевые, полные и native проверки; независимое ревью фактического diff | Закрыты подтверждённые блокеры, результаты привязаны к точному source SHA |
| 8. Собрать пакеты | Universal first-run APK, Android со встроенным тестовым URL, Windows EXE/ZIP; сохранить run/source/artifact/checksum | Пакеты получены из проверенного кода; тестовые URL и секреты не попадают в Git/публичные релизы |
| 9. Финализировать code PR | Удалить временные workflow-механизмы, повторить затронутые проверки, согласовать документацию и PR | Рецензент видит готовый diff и реальные ограничения; merge/release остаются отдельными действиями |

При разделении этапов на коммиты не оставлять промежуточное состояние с несовместимыми протоколом, submodules или generated-кодом. Повторно проверять изменение базовой ветки до создания PR реализации; плановый PR и текущая работа по реализации не должны перезаписывать друг друга.

### Полный набор и генерация

Использовать закреплённые workflow/команды из [.agents/commands.md](../../.agents/commands.md), адаптированные к donor v0.9.3:

1. `flutter pub get`; генерация Riverpod/freezed/drift через `dart run build_runner build --delete-conflicting-outputs`; локализации через `dart run intl_utils:generate`; Rust bindings при изменении API. Generated-файлы получают генератором, повторная генерация не меняет tracked output.
2. Dart format, `flutter analyze --no-fatal-infos`, полный Flutter suite и coverage. Если принят donor `tool/test.dart`, он остаётся проверяемым runner для `flutter test`. Проверить floor нового `lib/flashco`, не снижая старые.
3. `bash tool/check_plugins.sh`; отдельные analyze/tests `plugins/setup/setup_hooks`, которые root Flutter tests не покрывают.
4. `CGO_ENABLED=0 go test .` и `go vet .` в `core`; отдельные format/vet/tests для `modules/flashco_core`; NDK-backed Android Go compile/vet и Dart/Go protocol tests.
5. Android JVM/Kotlin checks; Rust crates и Windows Helper feature tests; debug builds Windows/macOS/Linux.
6. Personal Android/Windows packaging из чистого checkout с pinned submodules и SHA-256-проверенным CA bundle. Перед упаковкой build hooks включены.
7. Проверка установки поверх существующего Flashco на тестовом Android и Windows, согласие/VPN permission, reconnect, start→stop/restart, provider refresh и реальное подключение. Успешная компиляция не заменяет устройство/эмулятор.

Для агентского локального запуска действует `SAFE_MODE=true`; активное пользовательское приложение и его сеть не используются как тестовый стенд.

### Временные шаги в подготовленной ветке

В неопубликованном checkpoint есть push-trigger и артефакт с generated sources для первого получения результатов генераторов, а также форматирование/tidy в workflow. До финальной проверки нужно получить и закоммитить необходимые generated/lock изменения, убрать временный push-trigger и generated-source upload, вернуть personal workflow к ручному запуску. В рабочем CI должна проверяться воспроизводимость сохранённых исходников; незакоммиченные изменения сборочных inputs не должны скрываться.

## 9. Откат и критерии завершения

До тестового обновления сохранить согласованную копию базы и preferences при остановленной тестовой копии приложения. Проверить восстановление этой копии старой версией. Повышение схемы до 23 означает, что возврат старого EXE/APK сам по себе не является проверенным откатом данных. Не удалять таблицы и не откатывать пользовательские данные автоматически.

Реализация готова к рассмотрению на merge, когда:

- [ ] Все SHA, submodules, зависимости и конфликтные решения зафиксированы.
- [ ] Собственные функции выделены и не требуют патча внутри Mihomo submodule.
- [ ] Миграции проверены на существующих данных; настройки, профили и rules сохранены.
- [ ] Оба режима подписки, fallback на все серверы, DIRECT и REALITY проходят проверки итогового Core config.
- [ ] Updater и installer совместимы с идентичностью, подписью и реально доступными пакетами Flashco.
- [ ] Codegen воспроизводим, временные workflow-шаги удалены, целевые и полные проверки итогового source state завершены успешно.
- [ ] APK и EXE/ZIP связаны с проверенным source SHA, run ID, artifact name и checksum; отдельно записан результат device/upgrade проверки.
- [ ] Независимое ревью не оставило подтверждённых блокеров; актуальны PRODUCT (при изменении требований), project context, история и память.
- [ ] Проверена процедура восстановления данных; merge и release выполняются только по соответствующей команде пользователя.
