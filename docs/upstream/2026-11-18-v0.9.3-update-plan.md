## 3. Обязательные функции Flashco

Канон требований — [PRODUCT.md](../../PRODUCT.md). Ниже перечислены критерии, которые должны пережить обновление.

| Функция | Сохраняемое поведение |
| --- | --- |
| Два варианта подписки | Прежние Android/Windows-сборки со встроенным URL и дополнительный Android first-run без URL. Режимы встроенного URL и запроса при первом запуске взаимоисключающие |
| Первый запуск | Запрос после соглашения только на новой opt-in Android-установке; отмена и ошибка допускают повтор; завершение после сохранения профиля. Обновление, удаление профиля и ручной выбор не запускают импорт повторно |
| Персональные настройки | Применяются один раз по состоянию хранилища до миграции. Сохраняются выбранные тема, язык, автозапуск, TUN, auto-route, strict-route, системный прокси и запрет обхода VPN |
| Fallback | Штатная упорядоченная группа по всем узлам и providers, возврат к приоритетному живому узлу, интервал 10 с, timeout 3000 мс, `lazy=false`, HTTP 204. Если существующая группа опустела после фильтра/обновления provider — `empty-fallback: REJECT`. При применении fallback исходная конфигурация без подходящих root nodes и без определений providers вызывает `FormatException`. `DIRECT` и `Fastest` не становятся резервами |
| Число серверов | Искусственного ограничения нет. В основной ветке уже обходятся все серверы; тест на 350 узлах — пример регрессии, а не новый максимум |
| REALITY | Только при opt-in define добавляются отсутствующие ML-KEM/fingerprint defaults. Явные значения, включая `false`, сохраняются; HTTP/file/inline providers и их обновления покрыты; исходная подписка не переписывается |
| DIRECT | Российские домены/IP и адресные исключения остаются в редактируемых правилах. Сохраняются изменения, отключения, порядок и однократность backfill |
| Данные | Профили, URL, overrides, выбранные группы, пользовательские правила, markers и настройки не сбрасываются. Режим профиля с fallback остаётся стандартным |
| Идентичность | Сохраняются каталоги данных, FlashcoCore/Helper, IPC и Windows AppId. Официальный Android — `com.follow.flashco`; personal APK без release signing получает `.dev`. Совместимость обновления доказывается для фактического package ID и signer, а не имени файла |
| Windows | Сохраняются проверки версии/области/каталога, защита данных и работа только с Helper своей установки; подтверждённый downgrade не считается доказательством совместимости базы |
| Приватность | Firebase Analytics/Crashlytics не возвращаются. Внешняя проверка качества IP и Google ML Kit QR сохраняются по принятому решению; соглашение остаётся с одной кнопкой «Согласен» |
| Ранее удалённые функции | Не возвращаются продуктовая вкладка Safe, собственный failover, переключатель Fastest и редактируемые глобальные ML-KEM overrides. Защитный `SAFE_MODE` для разработки сохраняется |

Отдельная REALITY-конфигурация внутри XHTTP `download-settings` и явно выбранные старые fingerprints остаются за пределами существующего режима defaults. Обновление не должно обещать для них новую поддержку без реализации и проверки.

## 4. Границы собственного модуля

Выделение собственных функций согласовано в предшествующей задаче; оно нужно из-за пересечения Flashco defaults, подписки и маршрутизации с изменёнными donor bootstrap/setup/migration путями.

| Слой | Ответственность | Точки подключения |
| --- | --- | --- |
| `lib/flashco/` | Build flags, personal defaults, начальные DIRECT-правила, onboarding policy, выбор при импорте, fallback и REALITY transformations | `bootstrap.dart`, preferences, `providers/actions/profiles.dart`, `providers/actions/setup.dart`, финальное формирование YAML |
| `modules/flashco_core/` | Только собственная Go-политика определения ссылок на группы | Тонкий адаптер в `core/`, согласованный Dart/Go метод и контрактные тесты |
| Существующее хранилище | Запись профилей, preferences, транзакции и версии миграций | Остаётся у текущих owners; модуль не заводит вторую базу или независимый жизненный цикл |
| Платформенный runtime | Desktop Core lifecycle и Android `ServiceState` | Сохраняют владение start/stop/restart; модуль вызывает существующие интерфейсы |
| Mihomo submodule | Донорское ядро на точном SHA | Собственные политики Flashco хранятся вне `core/Clash.Meta` |

Для `lib/flashco` добавить измеренный coverage floor в `tool/check_coverage.dart`, сохранив существующие пороги. Для Go-модуля проверить build fingerprint/cache invalidation, `replace`/module path и форматирование отдельного каталога. Vet/compile и контрактные тесты выполнять в dependency context `core`, где объявлены `replace` на закреплённый Mihomo и локальный модуль. Самостоятельный `go test` из `modules/flashco_core` пока невоспроизводим: его фиктивная версия Mihomo разрешается через `core/go.mod`. Новых собственных `_test.go` там нет; содержательные проверки находятся в `core/profile_groups_test.go`. `no test files` не заменяет их прохождение.

## 5. Критические места совместимости

### 5.1. Коллизия миграции SQLite 21

В [Flashco](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/database/database.dart) миграция 21 добавляет российские правила. В [доноре](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/lib/database/database.dart) миграция 21 создаёт `ipQualities`, 22–23 создают/меняют `mitmModules`. Копирование donor `from < 21` пропустит нужную таблицу на установленном Flashco 21.

Рабочая схема — оставить Flashco backfill 21 и перейти к 23 через собственные этапы: 22 создаёт отсутствующую `ip_qualities`, 23 создаёт или приводит к текущей форме `mitm_modules`. Перед фиксацией SQL проверить фактические таблицы и колонки, включая старые и частично существующие формы. Создание таблицы и обновление уже существующей таблицы — разные сценарии. Транзакция не должна оставлять частично обновлённую базу.

Для существующей `mitm_modules` донорская схема 23 удаляет `update_interval_minutes` через `TableMigration`, сохраняя строки. Это подтверждено [donor migration test](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/test/database/migration_v1_to_v2_test.dart). Подготовленный `60925e7` вызывает только `_createTableIfMissing`, поэтому существующую старую таблицу не преобразует. До исправления и проверки этого случая checkpoint не проходит критерий миграции.

Обязательные fixtures: чистая установка; Flashco 20 и 21 с данными; промежуточная 22 с `ip_qualities` и отсутствующей, старой либо уже актуальной `mitm_modules`; повторное открытие; прерывание/ошибка транзакции; повторное обновление после отката, когда `user_version` ниже, а новые таблицы сохранились. Сверять профили, overrides, выборы, rules/disabled rules, IDs, порядок и MITM arguments/resources. Неизвестная структура требует отказа с диагностикой, а не принудительной смены номера схемы.

### 5.2. Версия preferences и новые overrides

Flashco использует `currentVersion=2`; донор — `1` и отдельный счётчик UI upgrades. Копирование donor migration может отклонить сохранённые данные Flashco как слишком новые. Сохранить совместимость версии 2, отдельно перенести нужные upgrade transforms и отказ от записи неизвестной будущей версии. Источники: [Flashco migration](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/common/migration.dart), [donor migration](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/lib/common/migration.dart).

Донорские `_upgrades` 1–4 меняют сохранённые значения. В Flashco нет их marker, поэтому буквальное копирование применит все этапы к существующей установке. Зафиксировать следующую политику:

| Donor transform | Решение для существующего Flashco |
| --- | --- |
| `_resetThemeColors` | Не переносить сброс; сохранить пользовательские цвета и выбор оформления, адаптировать только формат полей |
| `_keepGlassLook` | Не применять к обычным старым Flashco-настройкам, где такого поля нет. Совместимый reader для действительно существующего legacy glass-поля добавлять только с fixture его старого смысла |
| `_followSystemColors` | Не заменять сохранённую палитру новым набором цветов донора |
| `_turnOffSidebarBlur` | Не перезаписывать сохранённый `sidebarBlur`, включая явные `true` и `false` |

`currentVersion=2` продолжает определять совместимость данных/экспорта. Если нужен отдельный счётчик структурных upgrades, определить собственный список преобразований и записывать завершение только после успешного сохранения. Наличие методов `get/setUpgradeVersion` в checkpoint не означает реализованную миграцию. Проверить старую установку без marker, чистую установку, значения 0/1/4/неизвестное будущее, ошибку сохранения и повторный запуск с чтением из хранилища. Marker не продвигается после неудачной записи.

Проверить TUN `false` и пустые списки, DNS hijack, сохранённый test URL, размеры/положение окна, тему, WebDAV credentials и first-run/personal markers. Отсутствующее значение и явно пустое значение не эквивалентны. Отдельно проверить импорт старого Flashco ZIP с settings version 2/schema 21 новым клиентом: путь [readBackupArchive](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/common/backup.dart) проверяет обе версии отдельно от запуска приложения. Старый клиент должен корректно отклонять архив новой схемы; откат делается по предмиграционному снимку.

### 5.3. `profile.base` и итоговый YAML

[Новый Go-путь](https://github.com/chen08209/FlClash/blob/be84736605527034689c95bf27828ff27d912c5e/core/profile_base.go) держит большие списки в Core и при объединении берёт `proxies`, `proxy-groups`, `sub-rules` из исходного профиля. Поэтому Dart-only преобразования Flashco могут исчезнуть.

Первый совместимый вариант задаётся по реальным веткам `getProfile`:

| Сценарий | Ожидаемый путь |
| --- | --- |
| Не-custom профиль, нет непустого script, нет standard fallback, REALITY define выключен | `getProfileBase` → overlay → объединение в Core |
| Standard profile с сохранённым fallback | Полный `readConfig` → fallback; `profile.base` не используется |
| REALITY define включён | Полный путь для не-custom профиля, даже если исходный документ сейчас не содержит REALITY |
| Не-custom профиль с непустым script | Полный `readConfig` → script; standard fallback не применяется к script-профилю |
| Custom profile | Сборка из app proxies/groups, без `readConfig`/`getProfileBase`; injection только используемых providers |

Сохраняются существующие порядок сборки конфигурации и приоритеты значений. REALITY defaults применяются после script, provider injection, всех overrides/правил и перед YAML; general/TUN/sniffer stages не переставляются ради новой схемы. Этот порядок проверяется и для script/custom paths. Полный путь откладывает часть экономии памяти `profile.base`, но сохраняет собственные transformations; это принятое ограничение первого переноса, не повод ограничивать число серверов.

Нужны интеграционные тесты реального `getProfile` с выключенным и включённым `REALITY_SUPPORT_X25519MLKEM768`: проверять вызванный Core API и конечную конфигурацию, а не только предикат `requiresCompleteProfile`. В checkpoint enabled workflow повторяет только `reality_defaults_test.dart`, а `setup_action_test.dart` с этим define не запускается — этот пробел закрыть.

Проверять итоговую конфигурацию после объединения в закреплённом Core, включая refresh providers, root REALITY, явные overrides, DIRECT и ручной выбор. При применении настроенного standard fallback случаи 0/1/много узлов различаются: исходный профиль без подходящих root nodes и providers даёт ошибку; опустевший provider/filter существующей группы — `REJECT`. Это не новая общая валидация: DIRECT-only/custom/no-profile пути без fallback сохраняют прежнее поведение, включая пустой `BuiltProfile` при `profileId == null`. Валидная большая подписка, включая 350 узлов, проходит и полный путь, и соответствующий Core-контракт. Отсутствие программного лимита не является обещанием неограниченной производительности.

### 5.4. Updater, подпись и существующий выпуск Flashco

В [Gradle](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/android/app/build.gradle.kts) отсутствие release keystore включает debug-подпись и суффикс `.dev`, даже для release build. Personal Android workflows сейчас не предоставляют release signing. Готовый APK требуется инспектировать, а не выводить его идентичность из `namespace` или имени файла.

| Вариант | Package ID и проверка обновления |
| --- | --- |
| Официальный стабильный APK | `com.follow.flashco`, постоянный одобренный signer, проверенные versionName/versionCode и ABI |
| Personal/test APK без release signing | `com.follow.flashco.dev`; signer двух сборок может различаться. Update-in-place подтверждается только после проверки фактических старого и нового APK |
| Переход `.dev` → официальный APK | Разные приложения. Это отдельная установка с отдельно проверяемым переносом данных, а не обновление поверх |

Для готовых файлов записывать package ID, versionName, versionCode, ABI и signer SHA-256 через `apkanalyzer`/`apksigner`. При неизвестной или другой подписи не удалять старую установку ради «успешного обновления». Прежнее решение о постоянном клиентском канале и отсутствии отдельного клиентского `.dev`-канала сохранено в [проекте клиентских обновлений](../plans/2026-10-17-client-updates-design.md); наличие ключей/устройств сейчас не подтверждается этим планом.

**Переиспользовать уже существующий [release.yaml](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/.github/workflows/release.yaml).** Он запускается вручную из `main`, использует `flashco-release` и `PrepareAndroidSigning.java`, проверяет approved certificate через `ANDROID_CERT_SHA256`, формирует universal APK + Windows EXE/ZIP, manifest и `SHA256SUMS`, создаёт только draft release. Это отдельный путь от donor-ограниченного `build.yaml`; нового release pipeline не требуется.

Перенос обязан адаптировать и этот workflow: metadata preflight сейчас делает checkout без submodules, но перед `flutter pub get` потребуется новый path dependency `prism_ui`; в jobs, запускающих native hooks/packaging, нужен соответствующий SHA-256-проверенный CA bundle. Сохранить проверки `release_preflight.dart`, `release_bundle.dart`, `release_cli.dart`, выбор точного SHA и повторную проверку тега. Не передавать release-ключ в PR job и не ослаблять ограничение запуска из `main` ради предварительного теста.

**Версия результата.** В неопубликованном checkpoint подготовлено `0.9.3+2026111801`; это не выпущенная версия. Перед финальной упаковкой сверить ранее выданные реальные пакеты и опубликованную историю, затем закрепить выбранную Flashco version/build в source commit. Не копировать donor build number. Для очередного публичного обновления возрастают и видимая версия, и buildNumber, как требует [validatePublishedUpgrade](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/tool/release_preflight.dart): одного нового buildNumber при прежнем `vX.Y.Z` для текущего обнаружения обновлений недостаточно.

**Выбор пакета.** Основное Android-имя — universal `Flashco-X.Y.Z-android.apk` существующего Flashco pipeline. Донорские ABI suffix использовать только при наличии реально выпущенного совместимого asset. Проверять также вариант продукта: `release.yaml` сейчас собирает обычный stable APK без first-run/REALITY defines, а дополнительный personal workflow включает оба флага. Generic update не должен отключить REALITY defaults при следующем построении YAML. Пока для opt-in/test сборки нет одобренного совместимого пакета с тем же контрактом функций, in-app установку такого обновления не предлагать; отдельный `.dev`-канал этим планом не создаётся.

**Разные механизмы проверки.** Runtime updater обязан сохранить строгий TLS и отказ от установки при отсутствии `SHA256SUMS`, нужной записи, несовпадении хеша или отмене. SHA-256 файла не является проверкой Android signer. Идентичность, сертификат, ABI, `!debuggable`/`!testOnly` и содержимое bundle проверяются по готовым файлам существующими release tools; системный установщик остаётся отдельным барьером совместимости подписи. Проверить отсутствие latest/совместимого asset, сетевой сбой и отмену без нарушения работы VPN.

При повторной проверке API список доступных releases пуст. Actions artifact, draft release и опубликованный latest — разные результаты. Перенос updater проверяется fixtures до публикации, фактическое обнаружение latest — после отдельно разрешённого выпуска. Публичный пакет со встроенным личным URL и автоматическая публикация этим планом не предусматриваются.

При разделении этапов на коммиты не оставлять промежуточное состояние с несовместимыми протоколом, submodules или generated-кодом. Повторно проверять изменение базовой ветки до создания PR реализации; плановый PR и текущая работа по реализации не должны перезаписывать друг друга. Реестр конфликтов хранить с колонками «исходный путь/источник SHA → результат → принято/адаптировано/исключено → причина → проверка».

Подписанный клиентский `release.yaml` требует проверенный тег на `main`. Его фактический запуск относится к отдельно разрешённому этапу после merge, а не к недостижимому условию перед merge. До него проверяются исходники workflow, metadata/bundle/signing contracts и доступные тестовые пакеты; после него — точные подписанные файлы из draft и обновление устройства. Изменение только отчётных Markdown после сборки не требует пересборки, если явно сохранён source SHA и подтверждено отсутствие изменений кода/build inputs.

### Временные шаги в подготовленной ветке

В неопубликованном checkpoint есть push-trigger и артефакт с generated sources для первого получения результатов генераторов, а также форматирование/tidy в workflow. Порядок обязателен: получить и проверить generated/lock изменения → закоммитить их → убрать временные push/upload/нормализующие шаги → зафиксировать окончательный source SHA → финальные проверки и пакеты из его чистого checkout. Personal workflow возвращается к ручному запуску. Проверка не должна скрывать незакоммиченные изменения сборочных inputs; контрольная генерация подтверждает чистый tracked diff. После изменения кода, build inputs или workflow заново выполняются затронутые проверки, а пакеты относятся к новой ревизии.

## 9. Откат и критерии завершения

### 9.1. Полный снимок и восстановление

До первого тестового обновления сохранить согласованный снимок состояния тестовой установки:

- SQLite с профилями, правилами, overrides и выбором групп; файлы `profiles/<id>.yaml`, `scripts/<id>.js`, локальные providers и прочие пользовательские файлы, на которые ссылается конфигурация. Для provider caches указать, какие восстанавливаются и какие воспроизводимо пересоздаются.
- Всё фактическое preferences-хранилище платформы, включая markers `bundledSubscription.<hash>`, `bundledFallback.<hash>`, `personalDefaults.v1`, `subscriptionOnboarding`. Windows/Linux используют `shared_preferences.json`, Android/macOS — хранилище нативного plugin; копирование одного JSON не покрывает все платформы.
- Manifest снимка: исходные версия/build, платформа, identity установки, состав файлов, контрольные суммы и способ получения согласованного состояния. Снимки с личными данными не добавлять в публичный Git или открытые Actions artifacts.

Состав файлов подтверждается [path.dart](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/common/path.dart), [preferences.dart](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/common/preferences.dart) и [выбором preferences store](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/main.dart). Штатный [ZIP export](https://github.com/Artypoul/Flashco/blob/871a89e4d7da3fe4a484c193b2fbeccc57129c5b/lib/providers/actions/backup.dart) сохраняет снимок БД, `Config`/version и связанные файлы, но не все служебные preferences. Его успешный импорт не доказывает полный откат установки.

Перед файловым снимком остановить тестовый app/Core/Helper и закрыть SQLite handles. Если используются WAL/SHM, получить согласованную копию средствами SQLite либо холодный комплект относящихся к базе файлов; не копировать только живой `database.sqlite` и не удалять журналы для обхода ошибки. После обновления проверить восстановление предмиграционного снимка **старым бинарником** в изолированной тестовой установке: профили и скрипты читаются, правила/выбор/настройки совпадают, повторного onboarding/import нет. Затем повторить обновление до новой версии; отдельно fixtures покрывают оставшиеся новые таблицы после прежнего downgrade.

Возврат старого EXE/APK сам по себе не является откатом данных схемы 23. Не удалять таблицы и не менять `user_version` автоматически ради запуска старого клиента. Если доступ к platform preferences или старому совместимому пакету отсутствует, соответствующий restore/upgrade сценарий остаётся непроверенным и фиксируется как условие клиентского выпуска.
